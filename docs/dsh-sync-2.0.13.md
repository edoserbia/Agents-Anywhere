# DSH 任务无法同步到 Agents Anywhere —— 根因报告

症状：在 DSH Desktop 2.0.13 里提交任务后，Agents Anywhere 看不到该任务及其过程。

## 结论：不是 DSH 2.0.13 的协议变更，是**上行带宽**

DSH 2.0.13 的桥接协议与之前完全兼容（`protocolVersion: 1.0`，`projectionVersion: 2`，
`ackTimeoutMs = 6e4` 未变）。真正的约束是这条链路的上行带宽。

### 实测带宽（本机 -> closex.cc）

| 方向 | 速度 |
| --- | --- |
| **上行**（连接器 -> 服务端） | **19.4 KB/s** |
| 下行（服务端 -> 客户端） | 216 KB/s |

**上行比下行慢 11 倍。**

### 桥接的 60 秒 ACK 预算

DSH 桥接给每个事件批次的确认时限是 **60 秒**（`ackTimeoutMs = 6e4`）。
在 19.4 KB/s 下：

| 快照大小 | 所需时间 |
| --- | --- |
| 1 MB | 54 s |
| 2 MB | 108 s |
| 5 MB | 270 s |
| 14 MB | 756 s |

**任何超过约 1.1 MB 的快照都无法在 60 秒内确认。**

实测中最长的单个会话历史是 **14.2 MB**。

### 失效链

1. 连接器需要同步一个较大的会话快照（数 MB）
2. 上传耗时超过 60 秒
3. 桥接在 60 秒时判定 `sync.failed`，批次号停在 28-30
4. 连接器重新订阅，**从第 1 批重新开始**，进度全部丢弃
5. 循环往复 —— 因此失败总落在同一个批次号上

日志证据（桥接侧）：
```
event=sync.failed batchSeq=30 queuedEvents=548
```
50 次尝试全部从 batchSeq 1 重来。

## 本次修复的三个真实缺陷

即使带宽受限，以下三个缺陷让情况恶化到完全不可用；它们各自独立成立：

### 1. 服务端：能力重发布阻塞 ingest 响应（已修复）

`publish_connector_session_capabilities` 会遍历该连接器的**全部 633 个会话**，
而 ingest 处理器**同步等待**它完成。实测单次请求耗时 **61.5s 和 65.0s**。

修复：改为后台任务，按连接器合并为一次，ingest 立即返回。
实测服务端最慢操作从 65,000ms 降到 274ms。

### 2. 连接器：运行时串行同步（已修复）

扫描器逐个运行时同步，一个慢的 Codex 读取（实测 61s）会**阻塞 DSH 的确认**。
两者互不相关（Codex 读取不涉及 DSH 状态）。

修复：每个运行时独立并发执行，一个慢运行时只影响自己。

### 3. 连接器：就绪判断可能永久等待（此前已修复）

DSH 只在收到 `session.inventory.complete` 时才离开 `starting`，而 supervisor
在 `starting` 时拒绝一切操作。该事件不保证送达，原代码无超时。
修复：90 秒上限后即视为可用，摄入继续在后台进行。

## 仍未解决（需要产品决策）

上行带宽 19.4 KB/s 是链路事实，代码无法改变。要让大历史会话可靠同步，需要其一：

- 增量同步：只上传变化的部分，而非整个快照
- 分块上传：把大快照拆成多个小于 ACK 预算的请求
- 更大的 ACK 预算（需 DSH 侧支持）
