# Agents Anywhere 2.0.26

## 本次修复

- **发消息报 `runtime did not report its state in time`**：平台接收消息前必须先读一次 `session.state`（10 秒预算），而 Connector 里 DSH 的这条读取会把「来源状态」通知走**同步上传**——那条路会先把待上传的整个积压推完，再做一次到服务端的 HTTPS POST，且全程占着与历史快照共用的锁。实测复现：积压 512 条时，本应只发 1 条的状态读取实际发了 **513 条、9 个来回、1.81 秒**（无积压 0.20 秒）。来源状态是**最新值**（新旧互相取代），等落库没有收益，现在改走类型化的非阻塞通道。
- **活动回传要几分钟才到（更严重）**：DSH 插件是**停等**协议，34ms 一批（约 30 批/秒），一批没被确认就不再发下一批；而 Connector 要等一次公网上传完成才确认，实测只能跑到 **2.4–4.3 批/秒**。插件的 10000 条事件缓冲随即撑爆、整条流失败、**全部会话重新校准**，循环往复（一天 34 次，且每次 `queuedEvents=10000`）。现在**收到即确认**，操作按序交给单个工作者；**检查点**仍是持久化屏障——它要等数据真正落到服务端才推进，所以提前确认不会丢数据（崩溃只会从旧检查点重放）。
- **流式回复逐版重传整条内容（本次最大的一项传输优化）**：运行时每产生一次修订就重发**整条消息**，一次回复可达每秒约 30 版。按 10 KB 的回复算，需求约 150 KB/s，而实测上行只有 19.4 KB/s——超出约 8 倍。现在同一条目的最新版本会被按住一个窗口（默认 0.4 秒，`AA_CONNECTOR_TIMELINE_WINDOW_SECONDS`，设 0 关闭），**被取代的版本根本不发**。实测（30 次/秒持续流式输出）：每 0.4 秒一次上传，**30 次修订 → 3 次上传**。窗口的截止时间属于**该窗口的第一次修订**，不会因为后续修订而顺延——否则一条**从不停顿**的长回复会永远等不到发送时机，读者在回复结束前什么都看不到（这个反方向的坑我实测踩到过：连续 2 秒的流式输出**一次都没发出去**）。

- **顺序仍然严格**：任何条目都不能越过比它更早的条目。否则当「完整快照」随后落地时（快照是**整体替换**语义），被越过的增量会被静默丢掉。有专门用例守着。正在流式输出的条目每次修订都会移到队尾，所以它不会挡住后面的内容。
- **顺带把服务端的应用成本量了出来**：服务端处理通知约 **5.6–9.0 ms/条**，而且**批量越大单条越贵**（1 条 10.4 ms；500 条 4521 ms，即 9.0 ms/条），并不随批量摊薄。所以「一次塞得越多越快」是错的，连接器因此按 **64 条**（`FLUSH_MAX`）和 **256 KB** 双重上限分批，最坏约 0.58 秒一批。更要紧的是流式合并的效果：一个正在流式输出的会话，之前每秒要让服务端花约 **270 ms**，现在约 **22 ms**——**降低约 12 倍**，这才是「活动不再几分钟后才出现」在服务端那一侧的原因。
- **按字节分批**：每个请求上限 256 KB（`AA_CONNECTOR_INGEST_FLUSH_BYTES`）。上传失败是整批重发，无上限的请求会让一次网络抖动丢掉它携带的全部内容；现在每次成功的请求都是服务端已保存的进度。
- **gzip 请求压缩**：服务端新增有界解压中间件，并在 `/api/v2/health` 声明能力。Connector **只在服务端声明支持时才压缩**，因此新 Connector 连旧服务器、旧 Connector 连新服务器都正常。
- **大请求断点续传**：完整快照是**原子**的（服务端用它整体替换会话时间线，不能拆成几段分别应用），所以对慢链路只能暂存字节、按片续传。新增 `POST/GET/PUT/DELETE /api/v2/connector/ingest/uploads[/{id}]` 与 `.../commit`；偏移不符返回 409 并带上服务端实际持有的字节数，发送方从那里继续。暂存按 TTL 清理、按 Connector 隔离、有容量上限。**可恢复的失败不会丢弃已传字节**，只有确定性失败才回收。
- **客户端中途断开不再让服务端空转**：请求体读取循环原本把 `http.disconnect` 当作「继续等」——而服务端对**已经断开**的连接会一直回这个事件，于是循环**永不退出**、死死占住一个请求任务。移动网络上传到一半掉线是常态，正好会踩中。现在按框架惯例直接结束请求（实测：修复前 5000 次调用仍在循环，修复后立刻抛出）。
- **暂存体的编码走 `X-Upload-Encoding` 而不是 `Content-Encoding`**：创建请求自己没有请求体，而 `Content-Encoding` 描述的是**它携带的**请求体，请求解压中间件有权消费它。最初写成 `Content-Encoding`，端到端测试当场抓到了这个冲突。
- **链路抖动一次，Connector 就再也连不上（实机踩到且自愈不了）**：某次 websocket `keepalive ping timeout` 之后，Connector **连续一小时**每次请求都失败（`backend authentication request failed`，报错文本是**空的**），而**同一时刻 curl 访问同一个 URL 是 200**（12/12 成功），重启进程立刻恢复。
- **机制已确认，而且不用联网就能复现**：httpx 在**构造客户端的那一刻**就把代理端点固定下来。实测把环境里的代理从 `11111` 改成 `22222`：`getproxies()` 报的是 `22222`，而**已经建好的客户端依旧发往 `11111`**，只有新建的客户端才发往 `22222`。所以代理一旦迁移或失效，那个客户端会**一直拨号旧端点**——每次请求都超时、永不恢复，直到进程重启。
- **这条能解释全部现象**：持续一小时；curl 不受影响（每次重新读配置）；重启即恢复；报错文本为空（`ReadTimeout`/`PoolTimeout`/`ConnectTimeout` 的 `str()` 都是空串，而连接被拒是 `ConnectError`、文本非空）；每轮约 120 秒（connect 60 + read 60）。
- **为什么只有 HTTP 那一半坏了**：`websockets` 每次连接都会重新读代理（`get_proxy()` 在 `create_connection` 里调用），而 `run_once` 是**先鉴权再连 websocket**——鉴权被冻住的端点卡死，websocket 那一步根本走不到。所以只冻结了 HTTP 客户端这一处，修这一处就够了（其余 `os.environ` 读取都只在启动时读配置，属于设计如此）。
- **修法与验证**：每次连接尝试重建连接池（并关闭旧的），于是每次都会重新读取代理配置。两个用例锁住——一个断言循环**每次尝试都重建**，一个断言重连后用的是**新**端点。把代码改回「只在启动时建一次」，**两个用例都会失败**（已实测）。
- **代理环境变量导致 Connector 根本起不来**：从命令行启动时，若 `NO_PROXY` 含带方括号的 IPv6（`[::1]`，macOS 会把系统代理配置并进来），httpx 在**构造客户端时**就抛 `InvalidURL: Invalid port: ':1]'`，进程无法启动；而同样的构建从桌面端启动却正常（Electron 不继承 shell 环境）。现在启动时丢掉 httpx **用不了**的条目，保留所有能用的，`HTTP_PROXY`/`HTTPS_PROXY` 一律不动。
- **暂存传输按 Connector 限量**：单次上限 64 MiB，但**没有**限制一个 Connector 能同时开多少个——只靠 TTL 清理的话，持续开新传输就能把磁盘占满。现在每个 Connector 最多 8 个，超出时淘汰**最旧**的（正常 Connector 一次只暂存一个 body，最旧的正是最不需要的）。
- **一轮独立审阅（全新上下文，只给 diff 和必须成立的不变量）又抓出 8 处**，全部先复现再改，每处都有「把修复回退就失败」的用例：第二次被拒的通知没有被记录（屏障会对被拒数据放行）、被取代的条目没有唤醒等待中的屏障、暂存上传把 502/503/429 当成永久拒绝（**删掉已传字节**）、服务端在应用之前就释放暂存字节（失败重试要重传几分钟）、同步快照会越过 durable 积压（被越过的增量被整体替换丢掉）、旧通道替换承诺过的槽位会让水位线永久超前、旧通道的暂存区无上限、以及 worker 死亡时被阻塞的写入方永远不被唤醒（整条中继挂死）。
- **可观测性**：每个慢请求或大请求输出一行 `connector ingest upload notifications=… wire_bytes=… raw_bytes=… encoding=… elapsed_ms=… kbps=… queued=… durable=… batches=…`。以前只能从行为反推链路吞吐。

## 上线后的实测

- **≤17:40（旧连接器）**：34 次同步失败，**全部** `queuedEvents=10000`——链路健康时 Connector 自己跟不上、把插件缓冲撑爆。
- **17:40–17:50（已加载流式窗口）**：0 次。
- **17:50–18:52**：2 次，但**是我自己那个「连接池卡死」bug 的连带后果**——连接器根本传不上去，流自然超时。我一开始把它归因成链路抖动，是错的。
- **18:55 起（窗口 + 重连重建连接池 都已加载）**：**0 次**；同期连接器日志 947 条、0 warning / 0 error。这只是约 10 分钟的初步观察，**不是**长期稳定性结论。
- **一条被证伪的怀疑**：日志里常见的 `rpc.failed method=runtime.sync.ack code=INVALID_PARAMS` 看起来像「给已经换掉的流补发确认、把健康的新流打掉」。逐条对齐时间戳后不是——插件的流**先**失败，确认迟到才被新流拒绝。它是症状，不是原因，不需要改代码。
- **结论**：能减轻弱网的 gzip 与断点续传**要等服务端部署**才生效（Connector 会先探测能力声明，没声明就走整包明文）。不部署服务端，弱网这一半不会好转。

## 兼容性

- 服务端与 Connector 可分别升级：所有新能力都先由服务端声明，Connector 才使用。
- 旧 Connector 连新服务端、新 Connector 连旧服务端均不受影响（默认走整包明文 JSON）。
- 本次**没有数据库迁移**，线上库版本保持 `v2_38` 不变，因此回滚服务端不需要回滚 schema。

## 测试

- Connector：**1022 通过**。
- 服务端：**955 通过 / 18 跳过**。
- 除了两侧各自的单元测试，还补了**端到端**覆盖（走真实路由、真实令牌校验、真实 ingest 服务，并断言落库效果而不是状态码），以及**跨组件**用例：让 Connector 真实的 `ConnectorIngestClient` 直接对真实的 Server 应用收发。
- 改动量大，所以又在**真实 uvicorn + 真实 TCP + 真实令牌**下重跑了一遍（这次是全部改动之后）：明文 ingest 生效；20 KB 的 JSON 压缩后**只发 344 字节**（`content-encoding: gzip`）；900 KB **不可压缩**快照走暂存，**6 个请求**（创建 + 4 片 + 提交）、共 931,178 字节；30 次/秒的流式修订只产生 **3 次上传**；半截快照提交被 **422 拒绝**且会话不受影响。顺带在真实服务端上确认了拒绝路径：一条形状不合法的通知让屏障抛错、检查点没有前进。
- 更早一轮在同样的真实环境下验证过：明文与 gzip 落库一致、chunked 传输编码的 gzip 请求、断点续传「创建 → 6 次分片 PUT → commit」内容完整、5 条新路由存在、半截快照提交被 422 拒绝且时间线未改。
- `run_forever` 重建连接池那一行做了**变异验证**：删掉它，对应用例会失败（症状与线上一致），恢复后通过。只测重建函数本身是不够的——循环不再调用它时测试仍会全绿。
- **全量跑偶发失败与本次改动无关**：个别用例（`test_restart_recovery_fault_matrix[before_flush]`、`test_failed_history_publish_prevents_runtime_start`、`test_runtime_owner.py` 里的租约用例）在全量跑时会因负载时序偶发失败，单独跑稳定通过。已**直接对比**：切到 `main`（不含本次任何改动）连跑 4 次，**同样失败**（1005 通过 / 1004 通过 +1 失败，失败用例相同）。根因是它们共用全局的 runtime 租约文件与端口，属于既有的测试隔离问题。
- 端到端测试还抓到过一个会让本该 422 的请求变成 500 的问题：提交暂存体时若 JSON 解析失败，原实现返回的 `exc.errors()` 里 `input` 是**原始字节**，无法序列化进错误响应。半截快照因此既没被应用、也没被正确拒绝（`complete` 语义下误用会**整体替换**时间线）。
