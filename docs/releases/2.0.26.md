# Agents Anywhere 2.0.26

## 本次修复

### 1. 发消息报 `runtime did not report its state in time`

平台接收消息前必须先读一次 `session.state`（10 秒预算）。Connector 里 DSH 的
`get_session_state` 会把「来源状态」通知走**同步上传**：这条路会先把待上传的整个积压推完，
再做一次到服务端的 HTTPS POST，而且全程占着与历史快照上传共用的那把锁。于是 10 秒预算
花在了别人的上传上，状态读取永远不返回，消息根本没发出去。

复现（512 条积压时，本应只发 1 条的状态读取）：

```
backlog=    0  uploads=1  notifications_uploaded=1    -> 0.20s
backlog=  512  uploads=9  notifications_uploaded=513  -> 1.81s
```

来源状态是**最新值**（新旧互相取代，服务端只认最新一条），等落库没有任何收益。现在改走
类型化的非阻塞通道。

### 2. 活动回传要几分钟才到（更严重的问题）

DSH 插件是**停等**协议：34ms 一批（约 30 批/秒），一批没被确认就不再发下一批。而 Connector
原来要等一次公网上传完成才 ACK，实测只能跑到 **2.4–4.3 批/秒**。插件的 10000 条事件缓冲
随即撑爆，整条流失败并触发**全部会话重新校准**，循环往复。

实测（同一天的插件日志）：

| | 修复前 | 修复后 |
|---|---|---|
| `sync.failed` | 34 次 | **1 次** |
| 单条流存活 | 25–216 秒 | **93 分钟无失败** |
| 事件缓冲 | 每次 10000（满） | 855（未满） |

现在**收到即确认**，操作按序交给单个工作者处理；**检查点**才是持久化屏障——它仍会等到数据
真正落到服务端才推进，所以提前确认不会丢数据（崩溃只会从旧检查点重放）。

### 3. 弱网下的传输量

- **流式回复不再逐版上传（本次最大的一项）**：运行时每产生一次修订就重发**整条消息内容**，
  一次回复可达每秒约 30 版。这正是「聊天一多就传不动」的主因——按 10 KB 的回复算，需求约
  150 KB/s，而实测上行只有 19.4 KB/s。现在同一条目的最新版本会被**按住一个窗口**
  （默认 0.4 秒，`AA_CONNECTOR_TIMELINE_WINDOW_SECONDS`，设 0 关闭），被取代的版本**根本不发**。

  实测用例：连续 30 次修订 → **只上传 1 次**。

  顺序仍然严格：任何条目都不能越过比它更早的条目——否则当「完整快照」随后落地时，
  被越过的增量会被静默丢掉（快照是**整体替换**）。这一点有专门用例守着。

  这一项**不需要部署服务端**就生效。
- **同条目版本合并**：流式回复每秒被整条重发约 30 次，且体积随内容增长。等待上传期间现在
  只保留最新版本；链路越快，这个优化越不生效（因为根本来不及积压），链路越慢收益越大。
- **按字节分批**：每个请求上限 256 KB（可配）。上传失败是整批重发，无上限的请求会让一次
  抖动丢掉它携带的全部内容；现在每次成功的请求都是服务端已保存的进度。
- **gzip 请求压缩**：服务端新增有界解压中间件，并在 `/api/v2/health` 声明能力。Connector
  **只在服务端声明支持时才压缩**，因此新 Connector 连旧服务器、旧 Connector 连新服务器都正常。
- **大请求断点续传**：完整快照是**原子**的（服务端用它整体替换会话时间线，不能拆成几段分别
  应用），所以对慢链路只能暂存字节、按片续传。新增
  `POST/GET/PUT/DELETE /api/v2/connector/ingest/uploads[/{id}]` 与 `.../commit`；分片按偏移
  续传，偏移不符返回 409 并带上服务端实际持有的字节数。暂存按 TTL 清理，按 Connector 隔离，
  并有容量上限。**可恢复的失败不会丢弃已传字节**——只有确定性失败才回收。
  暂存体的编码走 `X-Upload-Encoding` 而不是 `Content-Encoding`：创建请求自己没有请求体，
  而 `Content-Encoding` 描述的是**它携带的**请求体，请求解压中间件有权消费它
  （最初写成 `Content-Encoding`，端到端测试当场抓到了这个冲突）。

### 4. 链路抖动一次，Connector 就再也连不上（实测踩到）

实机观察到的现象：某次 websocket `keepalive ping timeout` 之后，Connector **连续一小时**
每次请求都失败：

```
connector backend network unavailable error=backend authentication request failed: ; reconnecting in 3.0s
```

而**同一时刻用 curl 访问同一个 URL 是 200**（12/12 成功，约 0.2 秒）。重启 Connector 立刻恢复。

原因：`run_forever` 只在启动时构造一次 `httpx.AsyncClient`，之后每次重连都复用它。于是
「代理已经丢弃的连接」和「构造时读到的代理配置」都被一直沿用——链路抖一下，这个对象就永久
坏了，而且日志只说"网络不可用"，看起来像网络问题。

现在**每次连接尝试都重建连接池**（并关闭旧的）：坏状态最多影响一次尝试，代理配置变化也能
被重新读取。

这一条是本次修复里唯一**用户已经真实踩到且自愈不了**的问题。

### 5. 代理环境变量导致 Connector 根本起不来

从**命令行**启动 Connector 时，某些机器的 `NO_PROXY` 里含有带方括号的 IPv6（`[::1]`）——
macOS 会把系统代理配置里的条目并进来，所以没人主动写过它也会出现。httpx 会把每个条目
挂成 URL 模式（`all://[::1]`），解析失败：

```
httpx.InvalidURL: Invalid port: ':1]'
```

而这个失败发生在**构造 HTTP 客户端时**，也就是进程刚起来的时候——Connector 直接无法启动。
同样的构建**从桌面端启动却正常**（Electron 不继承 shell 环境），所以这个差异几乎不可能靠猜
发现。

现在启动时会把 httpx **用不了**的条目丢掉（保留所有能用的），`HTTP_PROXY`/`HTTPS_PROXY`
一律不动——需要靠代理才能连上服务端的部署不受影响。判断方式是直接调用 httpx 自己的解析
逻辑，而不是复制一份规则，因此不会随版本漂移。

### 6. 可观测性

每个慢请求或大请求会输出一行：

```
connector ingest upload notifications=1 wire_bytes=727 raw_bytes=600134 encoding=gzip
  elapsed_ms=1 kbps=866.6 queued=0 durable=0 batches=0
```

以前只能从行为反推链路吞吐，现在直接可读。

## 上线后的实测与仍存在的问题

修好之后在实机上观察的一段（16:20–17:23，63 分钟）：

| 时间 | 失败时的插件队列 | 之前 5 分钟内的链路事件 |
|---|---|---|
| 16:58:14 | 5（几乎空） | 16:42 websocket `keepalive ping timeout` |
| 17:16:37 | 41 | — |
| 17:20:34 | 8257 | 17:19 websocket `keepalive ping timeout` |
| 17:22:27 | 10000（满） | 同上 |

结论要说清楚，不能含糊：

- **自伤型故障消失了**。修复前 34 次失败**全部**是 `queuedEvents=10000`——链路健康时
  Connector 自己跟不上、把插件的缓冲撑爆。现在失败紧跟在 websocket
  `keepalive ping timeout`（链路黑洞约 20 秒以上）之后。
- **链路的锅还没解决**。上行 19.4 KB/s 且会黑洞时，任何 Connector 都追不上；能减轻它的
  正是 gzip 与断点续传——**而这两项要等服务端部署后才生效**（Connector 会先探测能力声明，
  没声明就走整包明文）。
- 所以：**不部署服务端，弱网这一半的问题不会好**。

另外记录一条**被证伪的怀疑**，免得以后有人重复排查：日志里常见
`rpc.failed method=runtime.sync.ack code=INVALID_PARAMS`，看起来像「Connector 给一条已经
换掉的流补发确认、把健康的新流打掉」。逐条对齐时间戳后并不是：

```
17:25:30 sync.failed batchSeq=467     <- 插件的流自己先失败了
17:25:30 sync.stopped batchSeq=467
17:25:30 rpc.failed runtime.sync.ack INVALID_PARAMS   <- 确认迟到，被新流拒绝
17:25:31 sync.started
```

确认被拒是**流已经死掉之后的症状**，不是原因；Connector 随后的重订阅是正确反应。
不需要为此改代码。

## 兼容性

- 服务端与 Connector 可分别升级：所有新能力都先由服务端声明，Connector 才使用。
- 旧 Connector 连新服务端、新 Connector 连旧服务端均不受影响（默认走整包明文 JSON）。

## 测试

- Connector：**1021 通过**。
- 服务端：**955 通过 / 18 跳过**。

除了两侧各自的单元测试，还补了**端到端**覆盖（走真实路由、真实令牌校验、真实 ingest
服务，并断言落库效果而不是状态码），以及一个**跨组件**用例：让 Connector 真实的
`ConnectorIngestClient` 直接对真实的 Server 应用收发（`server/tests/test_connector_server_wire.py`）。
只有这种用例能抓到"两边各自都对、但约定不一致"的问题——本次它抓到了一个：

- 提交暂存体时若 JSON 解析失败，原实现返回 `exc.errors()`，而其中的 `input` 是**原始字节**，
  无法序列化进错误响应，于是本该 422 的请求变成 500。半截快照因此既没被应用、也没被正确
  拒绝（`complete` 语义下，误用会**整体替换**时间线，属于会毁历史的那一类）。
  现在返回 JSON 安全的 `{"code": "invalid_ingest_body", ...}`。
