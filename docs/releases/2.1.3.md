# 2.1.3 — Connector：运行中会话的时间线同步与写锁占用者提示

本次只更新 Connector。Desktop、Web、Android、iOS、Server 与 DSH 插件保持 `2.1.2`
不变，接口与 `contracts/` 没有变化。

## 运行中会话的时间线不再冻结

Connector 的扫描器原先对所有“运行中”状态的会话直接跳过时间线读取，只把状态推给
Server，等会话空闲后才补一次整段历史。这条规则假设运行中的时间线一定由实时通道
覆盖：Codex 桌面/IDE 窗口通过 IPC follower 推送，Connector 自己发起的 turn 通过 SDK
通知推送。

当 Codex CLI（或 `codex app-server --listen unix://` 的 managed daemon）在**另一个
进程**里跑这个 thread 时，两条实时通道都不存在：没有窗口可跟随，turn 也不是
Connector 发起的。于是会话跑多久，AA 里的消息就停多久——现场表现为“Codex 一直在跑，
AA 只显示一小时前的消息”。

现在扫描器会对没有 IPC 实时流的运行中会话做周期性增量读取：

- 间隔由 `activeSessionSyncIntervalSeconds` 控制，默认 `120` 秒；配置为 `0` 关闭，
  恢复旧的“等空闲再同步”行为。也可用环境变量
  `AGENT_CONNECTOR_ACTIVE_SYNC_INTERVAL_SECONDS` 设置。
- 有 IPC follower 的会话（`state.metadata.attachment == "ipc"`）不参与，避免与实时
  推送重复。
- 读得慢的会话自动降频：实际间隔取 `max(30 秒, 配置值, 4 × 上次读取耗时)`。几百 MB
  的 thread 不会按 120 秒高频重读。
- 运行中读到的快照以 `complete=false` 发布：正在跑的 turn 永远不是最终时间线，不会
  覆盖 Server 上已有的完整快照。
- 每个会话第一次被观察为运行中时只记录时间不读取——连接器重启后的 recovery 已经读过
  一次，立刻重读只会让启动成本翻倍。

## 写锁冲突的报错点名占用者

`thread/resume` 返回 `already has an active writer` 时，错误信息原先只说“请先在原
Codex 客户端释放该会话；若仍被占用，退出对应客户端后重试”，用户无法判断要退出哪个
窗口。

现在会通过 `$CODEX_HOME/thread-writer-locks/<thread-id>.lock` 的持有进程（按打开文件
表定位，而不是猜测命令行）补一句 `当前占用者：<name> (pid N: <command>)`。锁文件在持有
者退出后会留在磁盘上，所以只有确实仍被打开时才点名；定位失败时保持原提示，不影响冲突
判定。

## 升级注意

- 仅 Connector 需要更新，其他端不需要同步升级。
- 新配置项可选：不写配置时按默认 120 秒生效。
- 已经在运行的 Connector 进程不会热替换。更新后应结束当前任务再完整重启 Connector
  或桌面客户端。
- 如果会话仍被外部 Codex 进程合法持有写锁，本次改动不会解除互斥：它只让**读**在运行中
  继续推进，写操作仍需该客户端释放会话。

  writer-lock 用例与 3 个 active-sync 用例）。

  把改动同步到 2.1.2 的源码目录后重启连接器，运行中的会话被重新读取并发布：

  ```

           runtime=codex session_id=sess_codex_8c58e28b… status=running
  12:28:06 existing session timeline sync published runtime=codex items=2 elapsed_ms=519.8
  ```

  同一份日志里，改动前的对应行为是 `existing session sync deferred active session
  … status=running` 连续出现 20 次以上且没有任何时间线发布。
