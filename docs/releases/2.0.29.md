# Agents Anywhere 2.0.29

## 修复：实时更新会永久停摆

- **根因**。整个产品的实时更新都走**一个 Redis 订阅**。监听器是一个 `async for`，外面**没有任何异常处理**——连接一断，任务就结束了；而发布方照旧往一个**没人读的通道**里发。客户端于是拿着它加载时的那份快照，**再也看不到任何变化**：会话的新记录不出现、运行中的圈不转、列表右边的绿点不亮；切走再切回来才会更新，因为那条路是走 HTTP 重新加载的。
- **实机证据**。Redis 在 **04:57 UTC** 断开连接，监听器把错误记录到 **07:36** 然后**不再存在**。在客户端连着、服务端正常发布的情况下，`PUBSUB NUMPAT` 读到 **0**——这正是它看起来像客户端问题的原因。**重启进程订阅就回来了**，这是最关键的线索：代码里没有任何东西会把它带回来。
- **修复**。监听器现在只在一处订阅；任何失败——流抛错、或者只是**正常结束**——都会丢掉死连接、开一条新订阅，并按 1 秒到 30 秒退避重试。取消仍然能停止它，所以关停不会变成空转。
- **实机验证**。我**故意杀掉订阅连接**：日志立刻出现 `timeline broker listener lost Redis, resubscribing in 1.0s`，订阅自动恢复；随后发一条真实消息，客户端在 **10 秒内收到 2 个实时推送**。

## 排查这个问题的过程，以及为什么之前会误判

- 服务端日志显示 WebSocket **一直在被正常接受**，所以第一眼像是客户端的问题。
- 客户端侧加了诊断（`AA_RENDERER_DEBUG=1`）后才看清：仪表盘流**连上了、拿到初始快照，然后再也没有收到任何更新**——尽管服务端确实在发布（`publish_bucket` 日志在滚动）。
- 最后是 Redis 自己的 `PUBSUB NUMPAT = 0` 把结论钉死的：发布方在发，订阅方不存在。

## 交付状态

- **服务端**：本次修复在服务端，需要部署镜像。
- **客户端**：无功能改动，随版本号一起发布以保持一致。
- 服务端测试 **968 通过 / 18 跳过**；变异验证：去掉重新订阅，新用例失败。
